About ZipToApk

ZIP project → GitHub → Android build pipeline.

This web companion follows the Android project's documented workflow: inspect the ZIP, detect dependencies, scan for secrets, confirm the GitHub operation, push source through Git data APIs, track GitHub Actions, then expose the APK artifact when the build succeeds. GitHub authentication and API access are brokered by the secure Cloudflare Worker session.

Guide · How ZipToApk works

Use this as the web equivalent of the Android app's Tutorial & Help.

1 · Connect GitHub

Use the secure GitHub connection button. Authorization is handled by web-auth.ziptoapk.in; the browser receives only the authenticated web session, not the GitHub OAuth token.

2 · Repository management

Select an existing repository, branch, or create a new repository. The push confirmation shows owner, repository, branch, commit message, file count, total size and attached-file status before anything is written.

3 · ZIP extraction & inspection

The ZIP is unpacked in-browser. Unsafe paths are rejected. Build/cache folders and generated artifacts are filtered so they are not unnecessarily pushed. Use Inspect to review the resulting file tree.

4 · Dependencies & additional files

Projects may need files such as google-services.json or a debug keystore. The Android app has dedicated detection and attachment flows; the web interface exposes the same concept before push.

5 · Secrets scanner

Credential-like patterns are checked before push. If findings exist, the safe path is to exclude the flagged files. You can explicitly cancel or bypass the warning, but bypassing should be treated as a deliberate risk.

6 · Full ZIP vs single-file update

Full ZIP push sends the project tree. Single File is for surgical hotfixes such as updating one source/config file without replacing the whole project.

7 · AI bug fixing

Gemini can analyze the project and propose complete file changes. Review the analysis and changed-file list, preview the relevant source, then explicitly apply changes. AI changes modify the current project buffer first; they are not automatically pushed.

8 · Build & percentage

After the GitHub commit/ref update, GitHub Actions performs the Android build. The tracker polls the workflow and calculates progress from completed workflow steps, showing the current step and percentage.

9 · Build failure

A failed workflow should expose the failure state and logs. Use Fix with AI to copy the failure context into the AI assistant, review the proposed changes, then rebuild only after confirmation.

10 · APK result

The Download APK action appears only after a successful workflow has produced an artifact. The artifact ZIP is opened, an APK is located, and the APK file is downloaded. A browser cannot silently install it like the Android app's package-installer flow.

11 · Versions / snapshots

Project versions are represented by Git commits. Download, restore and delete operations should use their own confirmation dialogs rather than executing destructive actions immediately.

12 · Remote announcements / FAQ

The Android app supports remote configuration for announcements, FAQs, tutorial videos and update information. The web companion exposes a refreshable control area for the same operational concept.
